I’m inspecting the implemented PR-011 through PR-014 code, deployment configuration, database policies, tests, and runtime boundaries before making any approval judgment. The review will distinguish verified controls from assumptions and will include concrete file references for every material finding.

The implementation review has already surfaced architectural claims that are not enforced by the code: the “append-only” timeline has no database immutability controls, LCM updates are last-writer-wins, and CAE executes synchronously without a claim/idempotency protocol. I’m now validating the surrounding auth, RLS, migration, build, and operational evidence so the final decision is based on reproducible defects rather than design criticism alone.

The verification evidence is materially below Alpha standard: the repository has no test files or CI workflow, root validation commands fail because declared workspace tools are missing, and the database policies do not grant event/health ingestion while granting overly broad mutation rights in several places. The remaining review is being consolidated into severity-ranked findings, explicit answers to the ten challenge questions, and a gated backlog rather than a redesign proposal.

Technical Due Diligence Report
Decision: DO NOT APPROVE

Project One is not ready for Alpha deployment involving real pets, physical devices, autonomous actions, pilot customers, or investor-facing production claims.

The implemented code demonstrates the intended domain separation, but the operational guarantees described by the architecture are not implemented. The system currently behaves like a server-rendered prototype with Supabase persistence, not a production event-sourced cognitive platform.

The most serious gaps are:

No reliable event-processing pipeline between Timeline, LCM, CRE, and CAE.
No idempotency or exactly-once-effect protection for actions.
No concurrency control for LCM state.
No immutable enforcement for the Timeline.
No device authentication model.
Incomplete and inconsistent RLS policies.
No retry, timeout, queue, circuit breaker, backpressure, or dead-letter mechanisms.
Hardware plugins are mocks and unsupported actions silently fall back to TabletPlugin.
No tests or CI/CD validation.
Declared root validation commands do not run because turbo and prettier are missing.

Direct Answers to Required Questions
Can Timeline become a bottleneck?
Yes.

Reasons:

Every event is stored as a full PostgreSQL row.
JSONB payloads are unbounded.
No partitioning or retention exists.
Realtime publication is enabled.
Queries use broad table reads and no cursor.
No ingestion queue or rate control exists.
No event aggregation or raw-vs-derived storage policy exists.
The Timeline can be adequate for a small Alpha with low event rates, but not for millions of animals or high-frequency sensors. Cameras must not send frames or frame-level detections directly into this table.

Can LCM become inconsistent?
Yes, very easily.

The implementation is read-modify-write with no locking, versioning, event ordering, replay protection, or monotonicity checks. Concurrent events and late-arriving events can overwrite newer state.

The last_event_id field is stored but not used to reject stale events.

Can Reasoning generate conflicting actions?
Yes.

CRE can produce multiple independent reasoning results from the same state. There is no:

Deduplication
Action arbitration
Priority conflict resolver
Cooldown
Mutual exclusion
Policy evaluation
Safety envelope
Model version
Input snapshot
Multiple rules can recommend contradictory actions, and nothing guarantees that CAE receives one coherent decision.

Can Action Engine create duplicated executions?
Yes.

This is one of the highest-risk defects. There is no idempotency key, unique execution constraint, atomic claim, or execution lease.

Concurrent approval, request retries, worker retries, or users double-clicking can duplicate execution.

Can plugins block the runtime?
Yes.

Plugin calls run directly inside the request path. There are no timeouts, cancellation signals, concurrency limits, circuit breakers, or worker isolation.

The current mock implementations do not prove that real integrations will behave safely.

Can SQLite synchronization corrupt state?
There is no SQLite synchronization implementation to assess.

The documented architecture claims edge SQLite WAL support, but no SQLite database, WAL, sync cursor, conflict policy, or reconciliation code was found.

If implemented later without deterministic event IDs, sequence numbers, durable outbox semantics, and conflict rules, corruption or duplication is likely.

Can Supabase Realtime become a scaling limitation?
Yes.

The system publishes multiple high-volume tables and subscribes broadly from the browser. There is no load test, connection budget, event coalescing, tenant-specific channel model, or fallback behavior.

Realtime should not be treated as the durable event-processing mechanism.

Can RLS policies become expensive?
Yes.

The policies repeatedly evaluate organization membership through subqueries, especially for telemetry and pet-linked tables. At high event volume and large tenants, policy evaluation can become a meaningful part of query cost.

RLS must remain enabled, but query plans need to be measured with realistic tenant sizes and indexes.

Can PostgreSQL indexes become inefficient?
Yes.

Current indexes are partly redundant and do not fully match the actual query patterns. The system lacks:

Query-plan validation
Partial indexes for active records
Composite indexes for common tenant/pet/time access
Index maintenance and bloat monitoring
Partition-aware index strategy
Indexing will degrade as append-only tables grow.

Can cache invalidation create stale state?
Yes.

The code claims LCM caching but has no explicit cache layer or invalidation contract. Server-rendered data, browser state, Realtime payloads, and database state can diverge.

What Is Good
The following decisions are directionally sound and should be preserved:

Separating Timeline, LCM, CRE, CAE, and plugins conceptually.
Using PostgreSQL RLS as a tenant-isolation boundary.
Keeping hardware integration behind a plugin interface.
Persisting reasoning results separately from current LCM state.
Recording execution metadata separately from requested actions.
Using Zod in several HTTP endpoints.
Using Supabase Auth session verification for guardian-facing routes.
Including explainability fields such as evidence, recommendations, confidence, and related events.
Treating the Timeline as the intended source of truth.
These are good foundations, but they are not sufficient without the operational controls listed above.

Final CTO Decision
DO NOT APPROVE

The architecture may proceed as an internal prototype or tightly controlled simulator Alpha after the core data integrity, authorization, and execution safeguards are implemented.

It should not currently be used for:

Autonomous physical actuation
Real veterinary or emergency decisions
Production health claims
Untrusted pilot customers
Offline device fleet deployment
Millions of animals
Investor claims that the described event-sourced runtime is operational
The project is not blocked by the high-level decomposition. It is blocked because the implementation does not yet enforce the safety, consistency, recoverability, scalability, and security properties that the architecture claims.
